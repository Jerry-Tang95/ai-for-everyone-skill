# 决策规则速查 — 《给所有人的AI入门课》

| 能力 | 一句话规则 |
|---|---|
| ML可行性双因素 | 用概念简单性 × 数据充足性两个独立维度定位项目——两者都满足才立即推进，任一缺失先补短板。 |
| ML项目流程 | 把 ML 项目当成收集→训练→部署→迭代的闭环，第一次训练几乎必然失败，部署后靠失败案例回流再训练。 |
| ML与DS项目判定 | 先问"最终产出是持续运行的软件，还是一份决策建议"——前者走 ML 工作流，后者走 DS 分析流程。 |
| 数据飞轮 | 只有"产品改进直接依赖用户产生的数据"时才有飞轮——用产品→用户→数据→更好产品的循环把领先变成壁垒。 |
| 自建还是购买 | 组件正在成为行业标准就购买采用，真正独特于业务、能带来差异化的才自建。 |
| 一秒法则 | 人类能在一秒内做出的判断，当前监督学习大概率能自动化；反之需几分钟的则暂不可行。 |
| AI价值三途径 | 每个 AI 项目必须能回答它降了什么成本、增了什么收入、创了什么新业务——三问都答不上来，价值存疑。 |
| 不等完美数据 | 数据不需要完美、够用就能开始——先定义"足够好"的门槛，达到门槛就建模，别无限期治理。 |
| 不为数据而收购 | 收购数据前先答"谁用、做什么用、怎么变现"——答不上来，"数据很有价值"就只是幻觉。 |
| 统计化验收标准 | 把验收标准写成"测试集达到 X% 准确率"而不是"零错误"，并为那部分错误提前设计兜底方案。 |
| 训练集测试集分离 | 测试集必须全程藏起来、只用一次做最终评估——用测试集调参等于泄露，报出来的数字就是虚高。 |
| AI项目生命周期 | AI 项目是六阶段闭环——先定业务目标，数据准备往往占 60-80% 时间，部署只是迭代的起点。 |
| 迭代而非完美 | 定义"能上线的最低标准"，达到就发布，建立反馈通道再持续迭代——完美不可达，真实反馈最珍贵。 |
| AI流水线设计 | 多模块串联时算端到端准确率（各模块相乘），先优化最薄弱环节，并让有人对端到端结果负责。 |
| AI战略护城河 | AI 本身很少是护城河——它放大你已有的数据、网络效应、品牌和规模优势，不会凭空创造优势。 |
| AI团队构建 | AI 团队是多学科组合——ML 工程师、数据工程、产品、领域专家、MLOps 缺一不可，先 3-5 人跑通再扩。 |
| AI转型路线图 | 五步走——先做试点积累势能，再建内部 AI 团队，然后全员分层培训，最后才制定战略并统一内外沟通。 |
| 自动化任务而非岗位 | 别想着自动化整个岗位——把岗位拆成一串任务，挑"简单 + 有数据 + 高价值"的那一个当第一个项目。 |
| 跨职能头脑风暴 | AI 项目创意长在"AI 能做什么"与"什么创造业务价值"两个圆的交集里——两类专家必须坐在一起找。 |
| 试点势能飞轮 | 第一个 AI 项目不该选最有价值的，要选最可能成功的——先建信誉与组织信心，让飞轮转起来再挑战高价值项目。 |
| 分层AI培训 | 别给所有人上同一门课——高管约 4 小时学决策、经理约 12 小时学管理、工程师 100+ 小时学构建。 |
| 从小处着手找伙伴 | 第一个项目只要"你能完成"就够——找一个懂技术的伙伴，别等准备好，做完第二个会比第一个好。 |
| 三重尽职调查 | 技术、商业、伦理三项尽调并行且必须全过——"技术上能做、商业上该做"不等于"伦理上应该做"。 |
| 统一数据仓库 | 把散落的系统数据汇聚到一个中央仓库，是 AI 转型最重要的第一步——但它是长期工程，要"边建边用"。 |

> 速查只给结论；需要原文依据、案例或反例时读对应能力卡。
